## Evaluate builds
The report is the same byte for byte as 0.15.0's. On the 54,000-game test database (Linux, 4 cores, synthetic), it took 419 s before and 360 s after (−14 %):

| Step | 0.15.0 | 0.15.1 |
|---|---|---|
| Reading the stored games | 28.5 s | 10.8 s |
| Fine-tuning | 86 s | 75 s |
| Patch memory on every held-out game, and early in a patch | 108 s | 85 s |

- **Reading on every core.** The stored games are now read and replayed on the model build's helper threads. Before, three cores waited while one did this.
- **Fine-tuning does less.** The item prior's settings now work out only the four item decisions. The other five are the chosen model's picks, which the same settings give them.
- **Patch ages are worked out once.** Before, they were looked up for every observation (1.8 % of the time).

## Safer memory
In the app, all of the middleware's threads share one 4 GB heap: the evaluation's, the model's and the fetching thread's.
- **The thread plan counts what's really in use.** The evaluation now clears its own leftovers before it plans its threads. Before, data it had just let go counted as used: 873 MB at 54,000 games, where 227 MB was really in use. At 54,000 games this leaves 2.0 GB for the other threads instead of 1.6 GB, which fits one more thread on PCs with 5 or more cores.
- **The other threads are measured.** While an evaluation runs, the app measures what the model and fetching threads use every 2 seconds. It keeps that plus a quarter plus 256 MB free for them, and never less than the 1 GB kept before. At about 118,000 games the model thread alone may use about 0.8 GB (estimate), which a fixed 1 GB didn't cover.
- **No model build starts while an evaluation runs.** A build holds two models for a moment, and in the shared heap that could run the evaluation out of memory. Builds that come due wait until the evaluation ends: in a test, a Data tab switch made during an evaluation rebuilt the model 13 s after it finished. The first build after starting the app doesn't wait.
- **The middleware's log shows the plan.** For example: `[eval] threads: 4 (… 2.2 GB of shared heap left, 1.0 GB kept for the app's other threads)`.

At your size most of the evaluation may still run on one thread. Each thread holds its own copy of the games, about 2 GB each at 226,000 games (estimate). Changing that is a bigger change; your `timings.json` and latest evaluation report would size it.
