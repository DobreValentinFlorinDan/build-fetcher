# Irelia Companion 0.8.6

**Evaluate builds is about 3.5 times faster** on a large database (36 min → 10 min on a 54,000-game test database), with the same report to the last digit.

Also fixes a remaining cause of **"database is locked"** while archiving old patches on Windows.

## Why it took up to 20 minutes
- **Every held-out game is compared with every training game**, for each decision of its build. With 30,000 games in the two newest patches, that is 30,000 held-out games against about 24,000 training games each, once per decision, so the work grows with the square of the games.
- **The evaluation does that several times:**
  - the bandwidth / prior grid (9 settings, on up to 2,000 held-out games per fold),
  - the final comparison on every held-out game,
  - patch memory's grid (3 fades per patch), then patch memory on every held-out game, where the older patches add another ~24,000 training games,
  - patch memory early in a patch, and the live replay.
- **Measured** on a test database of 54,000 games over six patches (30,000 in the two newest), one core: 35.8 min in all. The final comparison took 8.3 min and patch memory on every held-out game 15.5 min.

## Faster, with the same report
- **Only what is scored:** the evaluation scores nine decisions (keystone, secondary tree, summoners, start, max first, items 1–3, boots). It used to estimate the whole build for every held-out game, about 20 decisions; the rest (rune rows, secondary runes, shards, levels 1–3, items 4–6) are no longer estimated there. What you see in the app is unchanged: it still gets the whole build.
- **Each option in one tight loop:** the observations of a decision are grouped by option once per fold. Each held-out game then adds up an option's games in local variables, in the same order as before, so the sums are the same to the last digit and several times faster.
- **What doesn't depend on the draft is summed once:** with an infinite bandwidth, every held-out game used to sum the whole lane again. Now the lane's sums and each opponent's are kept.
- **The grid shares its work:** a draft's sums at one bandwidth are the same for the three priors (only the shrinkage differs), so they are added up once per bandwidth instead of three times. The similarities of the stored games to a draft are also computed once per bandwidth, on a flat array.
- **The live replay** compares each minute's game with the stored ones on the same flat array, so it uses the fast loop too.
- **Measured** on the same 54,000 games:

  | Step | 0.8.5 | 0.8.6 |
  |---|---|---|
  | Bandwidth / prior grid (5 folds) | 4.5 min | 35 s |
  | Final comparison on all held-out games | 8.3 min | 2.5 min |
  | Patch memory grid (5 folds) | 3.4 min | 67 s |
  | Patch memory on all held-out games | 15.5 min | 4.5 min |
  | Patch memory early in a patch | 82 s | 28 s |
  | Live replay (502 games) | 125 s | 34 s |
  | Reading the games, game-state model, interval | 41 s | 35 s |
  | **Total** | **35.8 min** | **10.3 min** |

  The report (chosen setting, lift, interval, Brier scores, patch memory's verdict) is the same to the last digit. Peak memory is lower on a large database: on the 54,000 games 0.8.6 peaks at 1.8 GB, where 0.8.5 was past 2.0 GB five minutes in (it builds 9 decisions' indexes instead of about 20). On small databases it is a little higher (518 MB against 477 MB on 2,200 games, 517 MB against 494 MB on 3,500).
- **Tested:** the estimator's kept sums give each prior exactly what a fresh estimate gives, and the flat similarities are exactly the per-game ones, with and without games missing a dimension. Whole reports came out byte for byte the same as 0.8.5's on three test databases (4,400 games of one patch, 4,400 over six patches, 6,300 over six patches).

## Fix: "database is locked" could still appear while archiving on Windows
- **Found by** 0.8.5's own lock test, which failed once on the Windows test machine while this release was checked. Archiving old patches waited 5 s for the database and gave up with "database is locked", while a thread shaped like fetching wrote every 20 ms.
- **Why:** every commit waited for the disk while holding the write lock. On a slow Windows disk that is tens of milliseconds, so a thread writing often held the lock nearly all the time, and the archive kept missing the moments it was free.
- **Now:** commits no longer wait for the disk (SQLite's recommended setting for this mode). The log is still written to the disk at every checkpoint. If the app crashes, nothing is lost; after a power cut, the last moments of fetching can be missing (they are fetched again), and the database is never corrupted.
- **Tested:** with every disk flush slowed to 20 ms, the archive failed every time before and passes now, also with 50 ms. The test itself no longer hangs when it fails: its writer thread stops either way.
