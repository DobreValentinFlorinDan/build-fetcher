# Irelia Companion 0.12.0

**Evaluate builds now needs less than half the memory per thread, so the same free memory runs it on about twice as many threads, and it is faster on any number of threads.** The results are the same to the last digit.

## Less memory per thread, so more threads
Measured on the 54,000-game test database with 4 threads, back to back on the same machine:
- **Each extra thread:** 427 MB at its peak instead of 967 MB.
- **The whole evaluation:** 2.3 GB at its peak instead of 4.8 GB.
- **The time:** 6.5 min instead of 7.4 min. That machine was slower that day than in the 0.11.0 notes.

**What this means on your computer** (16 threads, 16 GB, about 6.6 GB available, about 94,000 games read; estimates):
- **Before:** 0.11.0 planned 3 threads at about 2.1 GB each.
- **The first evaluation on 0.12.0** plans with 10,500 bytes per game read: about 0.9 GB per extra thread. The same 4.2 GB to spare beyond the 2.4 GB kept free then holds 5 threads.
- **The ones after it** plan with what it measured on your computer. On the test database that came to about 9,100 bytes per game: about 0.8 GB per thread, which holds 6.
- **With more free memory:** each extra gigabyte free when you click Evaluate builds holds about one more thread, up to your 16.

**What changed** (each keeps every number the same):
- **Only the first thread keeps results.** The other threads hand back their games' results and move on. The first thread adds them up in the same order as before, and shares just the choices that steer later work:
  - the bandwidth and prior;
  - patch memory's fade per patch;
  - the expected win rates.
  
  Before, every thread received and added up every result.
- **One fold's models at a time.** Before, the last fold's models stayed in memory until the next fold's were built, and the memory kept growing to about twice what was in use before it was cleaned up. Each fold's work now runs on its own, and memory is cleaned up before the next fold's models are built. "Patch memory early in a patch" now handles its two models one after the other instead of together.
- **Smaller copies of your games.** To score items, every thread used to keep the game state at each purchase (28 numbers per item). The chance of winning at each purchase is now worked out once, after the game-state model is fitted, and shared by all threads; the purchase states then go. Each thread's copy of the games is about 40% smaller.

## Faster on any number of threads
- **Shared out across the threads:**
  - The confidence intervals: four per evaluation, 1,000 resamples each. 6.3 s → 1.7 s on 4 threads.
  - The five fits of the expected win rate: 17 s → 6 s on 4 threads.
- **Less overhead:** the other threads no longer receive and add up every result.
- **A check done once:** each draft used to re-check every stored game's draft data before comparing them. It is now checked once per model.
- **On one thread:** about the same time as before. The extra memory clean-ups cost about what these save.

## Also
- The Data tab's memory figure per thread is measured afresh: 0.11.0's measurement (twice as much) isn't used.
