# Irelia Companion 2.2.0

**2.2.0 measures how trustworthy the app's win-chance model is, shows whether an item is mostly bought when already ahead, and tests two better ways of scoring purchases on your own games. A new way is used only if it beats today's on held-out games.**

## Background
The app rates every purchase by *win probability added*: the game's result minus the win chance just before the item was bought, averaged over games like yours. 2.2.0 builds on Perttu Jalovaara's 2024 Aalto University thesis, *Win probability estimation for strategic decision-making in esports*. The thesis supplied three methods: measuring the win-chance model's calibration, reporting the win chance an item was usually bought at, and ending an item's effect when it is sold or upgraded. No text or code is taken from it.

## What's new
- **How far to trust the win chance.** Each evaluation now reports the game-state model's *expected calibration error* (ECE) with a reliability table (20 bins), overall and for 0–10, 10–20, 20–30 and 30+ minutes. A well-calibrated model's 60 % wins about 60 % of the time; a large ECE in a time window means the item scores from that part of the game are less reliable. The log has one line per window.
- **W̄ beside each item.** The Items view now shows W̄, the average win chance at the moment players bought that item, using the same weighting as its score. Beyond ±8 points from 50 % it adds *mostly bought when ahead* or *mostly bought when behind*. An item bought mostly when ahead can have a high win rate without being better; its score already corrects for that, and W̄ shows why.
- **Two candidates, decided by your evaluation.** A full Evaluate builds tries both and keeps each only if it wins on held-out games; the log names both scores and which was kept:
  - **One game state per 5 minutes** to train the win-chance model, instead of evenly spaced frames, so the late game isn't under-sampled. Kept only with a lower held-out log loss.
  - **An item's effect ends when it is sold or upgraded.** A component is scored until it becomes the finished item, and a sold item until it is sold, instead of to the end of the game. Items kept to the end are unchanged. Kept only if the build's lift and the lower end of its 95 % interval both improve. The next-buy advice uses whichever definition was kept.

  A quick update reuses the choices of the full evaluation it builds on.

## Same results unless a candidate wins
- With both candidates off, every number is bit for bit what 2.1.1 gives: the full evaluation, the quick update and 200 sampled drafts. That was checked on the test data, on 1 and 3 threads.
- On the test data, neither candidate beat today's method, so on that data the app keeps today's results. On your games the evaluation decides.
- A full evaluation takes about 4–24 % longer, because it measures both candidates.

## Data
- No change to stored games, timelines or settings. The evaluation files gain a few optional fields (`reliability`, `sample`, `window`); older files still load.
- Nothing new leaves your PC.
