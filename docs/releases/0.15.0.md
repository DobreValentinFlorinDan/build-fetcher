# Irelia Companion 0.15.0

**Steadier in champ select, lighter in the background, and builds that can tune themselves once the data shows a gain.**

## Steadier
- **No model build starts while you're in queue.** In Matchmaking and Ready Check, champ select can begin any second, and a build that started then held the model thread through it. One log showed 38 "The model is busy" refusals and 12 failed live re-ranks.
- **Requests are answered during a build.** A build now prepares its games on helper threads, and the model thread answers with the model it has meanwhile. Before, every request waited for the build, up to 30 s, then failed.
  - Queue, champ select or a game stops a build that's running, and the model stays as it was.
  - The first build after starting the app always completes.
- **Slim stored data has a Stop button.** It undoes what the run did so far: from the slimming on, it puts the backup back. Before, the only way out was quitting the app.

## Lighter in the background
- **The model rebuilds when new data matters.** That means 1 % of the games it was built from (at least 50), after half an hour at the soonest, or six hours at the latest.
  - Before, every change rebuilt it after 5 minutes: about every 10 minutes while fetching, at a minute of one core each at 118,000 games.
  - Your own new game, a new patch and the Data tab's switches still rebuild it soon.
- **Faster builds, the same model.**
  - From 4,000 games, the games are prepared on helper threads: every core but one, as free memory allows, at most 6. They're put back in the order they were read.
  - A game's replay does less work.
  - On the 54,000-game test database with compressed timelines (30,000 model games; Linux, 4 cores; synthetic), the same games come out byte for byte:

    | Version | Build time |
    |---|---|
    | 0.14.4 | 17.7 s |
    | 0.15.0, one thread | 15.4 s |
    | 0.15.0, three helpers | 8.2 s |

  - **Estimate:** on more cores, about 2–3 times faster than 0.14.4.
  - Instead of a stored table of per-game features (an estimated 0.5–1.2 GB more on disk at 226,000 games), the work is spread over the cores, so the database doesn't grow.
- **Opponents in champ select switch faster.**
  - The lane builds read the stored games once per data change and validate them once per patch rule. Before, each new opponent did both again: about 1.3–2 s at 54,000 games, more at your size.
  - Measured in the built app on the test database (Linux): 0.23–0.31 s per new opponent, and 6 ms for one already seen.
  - The games are let go 3 minutes after the last use.
- **Automatic evaluations run after 3 % new games** (at least 300) or a new patch, still at most every 6 hours. Before, 300 new games were enough, while an evaluation's time grows faster than the games.

## Builds: fine-tuning, evaluated first
Three settings that were set by hand can now be tuned. Each is tried against the chosen draft model on the same held-out games:
- **Pilot standing's strength.** The pilot weight (source, tier, mastery, LP) is tried at strength 0, 0.5 and 2. 1 is as before; 0 counts every pilot alike.
- **The item decisions' own prior.** Core items, boots, items 4–6 and the live "Next" are tried with another of the evaluation's priors than runes, summoners, the start and skills.
- **A fade within the current patch.** A game of its region's current patch counts half after 7 or 21 days. Older patches stay with patch memory.

How the settings are judged:
- Each setting is tried alone, then the better ones together on every held-out game.
- **They're used only if** the result beats the chosen model with 95 % confidence, with a Brier no worse.
- Until then the app keeps today's settings. The Data tab says what the evaluation chose and whether it's in use, and the report has a **Fine-tuning** section.

The evaluation also changes in two ways:
- **A larger sample for its choices.** The bandwidth, the prior and fine-tuning are chosen on up to 10,000 held-out games instead of 2,000, which was under 2 % of the games at 118,000.
- **A fairer check, reported only.** The report adds the lifts compared **within each pilot**: followed against not followed by the same pilot. This way a model isn't credited because the pilots who follow it are better players.

Cost: on the test database the evaluation took 253 s before these and 386 s after them (+53 %). Patch memory, runes against the draft and the rest of the report are as before.

## Also
- The Slim stored data check was measured at 54,000 games: about 2 GB at its peak with 3 threads. It sizes its threads by the free memory, so it's unchanged.
- Data and policy are unchanged: Riot API and Data Dragon only, nothing leaves your PC, and no new dependencies or schema changes.
