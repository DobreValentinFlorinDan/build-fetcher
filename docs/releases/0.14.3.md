## Starts again after a Slim stored data run was cut short
- **The problem:** a Slim stored data run cut short is rolled back at the next start, before anything opens the database. On a large data folder, that rollback takes several minutes: copying the database's backup and checking it twice, then putting back every cache entry the run moved out. The app gave its middleware 90 s in all to start. So it ended the rollback part-way, said it couldn't start, and did the same at every start after. The log showed only `starting middleware` lines.
- **No data was lost:** each attempt starts the rollback over from the backup, which stays until the rollback is complete.
- **The start now waits for as long as the middleware says what it is doing.** Until it's ready, the middleware reports every 2 s, and only 90 s without a word ends it.
- **The splash shows the rollback,** for example "copying the database's backup (2,140 MB)", "checking the copy (SHA-256): 1,024 of 2,140 MB" or "putting the cache entries back: 120,500 of 410,000". The log gets one line for each part, and the result at the end.
- **The cache entries go back 500 at a time,** each batch checked byte for byte. Before, they were all read into memory at once, which could be many GB. A rollback cut short again carries on correctly at the next start.
- **Roll back** (of a verified run) and the automatic rollback after a difference use the same batches.
