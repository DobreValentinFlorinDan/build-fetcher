## How long, before and during
- **Before you start:** the buttons say how long the action should take, e.g. "Evaluate builds · Takes about 10 min (estimate)" or "Compact database · about 20 s". The same estimate is in the confirmation for the actions that delete something.
- **While it runs:** a bar made of small vertical segments fills from the left; the segment at the front pulses while it works. Under it: the time so far, how far it is, and the time left, always marked as an estimate.
- **Where the estimates come from:** each action's time is kept on this computer, never sent anywhere (`timings.json` next to your settings). The next estimate is the last run, scaled to the size it has now (more games, a bigger database). While an action runs, its own pace takes over as it goes.
- **For Evaluate builds:**
  - Each step counts by how long it took last time. Its steps differ a hundredfold: a few seconds for some, minutes for others.
  - Within a step, by the held-out games done, so the bar keeps moving.
- **First time:** the first time an action runs on your computer, Evaluate builds and Compact database start from what they took on the test database. The others say "estimating the time left…" for a few seconds, until their own pace says more. From the second run on, every estimate is your computer's own.

## Covered
- **Data tab:**
  - Evaluate builds;
  - the model's rebuild ("Updating the model…", also under the switches);
  - the data audit;
  - Rebuild from cache;
  - archiving and restoring old patches;
  - each region's fetch queue at its current pace (an estimate the queue outgrows while fetching runs).
- **Settings → Storage:**
  - Compact database;
  - Clear entire API cache;
  - Clear expired API cache;
  - Remove old Data Dragon patches;
  - Delete games of old patches;
  - Keep the API cache to the six-patch window;
  - moving the data folder.
- **Same segments:** the API rate windows (Data tab) and the overlay's gold towards the next item use the same segments. The overlay shows no time: nothing in game says when.

## Evaluation speed: what was tried
Profiled on the 54,000-game test database:
- **Where the time goes:** three-quarters of an evaluation compares each held-out game with every training game of its fold. Each game's draft similarity to every training game takes 38%, and adding up their results takes 37%. The rest of the work is small.
- **Tried, the same results to the last digit, but dropped for memory:**
  - **Sharing the similarities across the three patch-memory fades:** 2% faster, but 520 MB more at its peak.
  - **Comparing runes against the draft in the same pass as the builds:** 6% faster, but 220 MB more.
  - The evaluation alone peaks at about 1.3 GB there, so neither is worth it.
- **Kept:** a tighter similarity loop, with the same arithmetic in the same order. The reports are the same byte for byte on three test databases, and the peak memory is the same. It made no measurable difference on the test database, whose games miss most draft details. It can only help on drafts where every detail is known.
- **What would make it much faster:**
  - **Running the five folds side by side on several cores:** the same results, about 2–3× faster on four cores (an estimate). It needs roughly 0.6–1 GB more memory while it runs (also an estimate).
  - **Comparing a sample of the held-out games:** also about 2–3× faster, but the numbers come out slightly different.
  - Both were left out before. Say if you want either.
