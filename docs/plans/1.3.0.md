# Work brief: Build Fetcher 1.3.0, a stat-aware model and a dormant team network

## Goal (from the user)
- **A:** the model understands League's stats and combat math, not only item names.
- **C:** a larger "team network" ships too. It lies dormant and keeps watching the amount of data. Once enough games
  with timelines exist, it wakes up, trains, and goes live only if it beats the model in force.

## Rules
- **Data:** only Data Dragon (Riot's static data). No wiki and no CommunityDragon: the user's source rule and Riot's
  "use supported services for data ingestion".
- **Inputs:** only what the player sees in game: their own gold and items, and every player's champion, level and
  items from the Live Client.
- **Guardrail:** as strict as before. New inputs start at zero, so the model in force predicts exactly as before.
- **Reporting:** measure what's cheap to measure and say what isn't verified. Tests: Data Dragon parsing, the combat
  math, the network's gradients, and the dormant/awake gate.

## A. Stat-aware model
1. **`bf_core::ddragon`:**
   - Each item's full stat list, read from its description's `<stats>` block, with the `stats` object as a fallback.
     20 stats: AD, AP, attack speed, crit chance, crit damage, lethality, armor pen %, magic pen flat and %, ability
     haste, HP, armor, MR, life steal, omnivamp, heal and shield power, move speed flat and %, mana, tenacity.
   - Each item's effect flags: on-hit, active, aura, slow, wounds, shield, health-based damage, spellblade.
   - Each champion's base stats and growth per level.
2. **`learn/combat.rs`:** a 36-number combat vector for one player at one minute.
   - 20 build stats per 1,000 gold, so the values don't simply grow with game time.
   - 16 combat terms:
     - physical and magic damage that gets through the enemy's armor and MR, and the two mixed by the player's
       damage type;
     - effective HP against the enemy's damage mix, and the ratio of the player's to the enemy's;
     - crit × attack speed and on-hit × attack speed;
     - ability haste × caster;
     - life steal against anti-heal, and anti-heal against healing;
     - wasted crit, MR, armor and penetration;
     - off-damage-type stats;
     - build gold.
   - It uses each player's level, base stats and items. Samples get it from the timeline; the overlay gets it from
     the Live Client.
3. **Logistic model:** a new weight region after the enemy region (2^16 slots, starting at zero).
   - Shared: one weight per combat number (36).
   - Per champion-role: each champion's own value for each combat number. "Irelia likes attack speed" is learnt this
     way.
4. **Overlay:** each candidate item is scored with the combat vector recomputed with that item added.

## C. The team network (dormant until enough data)
- **Inputs, for each of the 10 players:** champion embedding, mean item embedding, build stats per 1,000 gold, base
  stats at their level, and level.
- **Shape:** one shared player network (51 → 32 → 24), then pooling into me, allies and enemies. A head takes the
  pooled values plus the game state and the player's combat terms (99 → 48 → 1).
- **It adds to steps 1 + 2.** Its last layer starts at zero, so when it wakes up it changes nothing until trained.
- **Dormant until `LearnConfig.team.threshold` games with timelines, 200,000 by default.**
  - The count is the stored timeline games when the app starts, plus every timeline game learnt after that.
  - The Model page shows the progress.
- **Once awake:**
  - it learns every new game, as the other steps do;
  - it also works through the stored backlog, 300 games per call;
  - each check judges it on top of steps 1 + 2, with the same guardrail.
  - **Accepted:** it is saved as a `team-nn` checkpoint, and the in-game advice adds its residual.
- **CPU only** (about 70,000 weights). No GPU kernel for it in 1.3.0.
