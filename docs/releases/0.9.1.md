# Irelia Companion 0.9.1

**Less memory when idle:** on a 54,000-game test database, the app's background part (the middleware) now settles at about 450 MB instead of about 830 MB. The model, the builds and the evaluation's results are unchanged.

## Why the app used about 1.5 GB when idle
Measured on a 54,000-game test database (patch memory on), the middleware alone held about 830 MB at rest. What it actually needs is 212 MB of model data, 15–20 MB for the main part and 8 MB for fetching. The rest was left over:
- **The model rebuild's leftovers (about 400 MB):** every few minutes while new games arrive, the model is rebuilt from all stored games. The build grows the memory a lot while it works, and afterwards the JavaScript engine kept those pages for later instead of giving them back.
- **Small freed blocks (about 200 MB):** the build creates 54,000 small arrays of game-state frames and frees them at the end. The system's allocator kept most of that memory for the app instead of returning it.
- **The champ-select cache (about 230 MB):** 0.9.0 keeps work between champ-select picks and lets it go 3 minutes after the last one. But while fetching, new games refresh the dashboard's build about every 30 seconds, so it never sat idle long enough to go.
- **Evaluate builds:** while an evaluation runs, the middleware holds about 1.5 GB. With Follow the evaluation on, the automatic evaluation runs exactly when you're idle (after 10 minutes without champ select or a game, at most every 6 hours), for about 10–20 minutes at that size.
- **The windows:** the dashboard and the overlay are browser windows. With the app's own Electron process they add a few hundred MB on top (not measured here).

## What changed
- **After a rebuild, the engine gives its spare memory back:** the model thread runs the JavaScript engine's thorough collection, which compacts the memory and returns the empty pages to Windows, then once more 2 seconds later. It takes about half a second at that size, and never during champ select or a game. It also runs whenever a cache is let go.
- **Frames in large blocks:** the build and the evaluation take their game-state frames from 16 MB blocks, which go back to the system as a whole when freed.
- **The champ-select cache only in champ select:** outside it, the dashboard's build is computed without it (about a second, in the background, as before 0.9.0), so nothing stays behind while you fetch. In champ select, picks after the first stay fast (tens of milliseconds).
- **The game's "Next item" data goes when the game ends,** instead of staying until the next rebuild.

## Measured (54,000 games, patch memory on, Linux)
| | 0.9.0 | 0.9.1 |
|---|---|---|
| Middleware at rest after a rebuild | ~830 MB | ~450 MB |
| … of which the model's own data | 212 MB | 212 MB |
| During a rebuild (peak) | ~1.2 GB | ~1.15 GB |
| While Evaluate builds runs | ~1.5–1.65 GB | ~1.5–1.65 GB |
| After an evaluation | — | ~740 MB on Linux (its allocator keeps some of what the evaluation freed; Windows' allocator wasn't measured) |

The builds, the evaluation's reports and the champ-select answers are the same to the last digit (tested). The middleware's numbers come from Linux; Windows' Task Manager counts memory differently, so expect similar savings rather than the exact figures.

## If memory still matters
- **Patch memory** off keeps 30,000 games in the model instead of 54,000: about 123 MB of model data instead of 212 MB.
- **Follow the evaluation** off stops the automatic evaluations, and with them the 1.5 GB while they run. You then run Evaluate builds yourself, and patch memory and runes against the draft stay as you set them.
